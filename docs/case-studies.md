# 문제 해결 사례

## 1. 비용은 지불됐지만 타워가 생성되지 않는 불일치 방지

### 문제

건설은 그리드 검사, 설치 개수 제한, 자원 지출과 프리팹 생성으로 이어집니다. 일부 단계만 성공하면 비용만 사라지거나 점유 정보만 남는 불일치가 발생할 수 있습니다.

### 해결

`TowerPlacementService`가 구매 흐름을 하나의 트랜잭션처럼 조정하도록 했습니다.

1. 타워 데이터와 프리팹 검증
2. 전체 footprint의 배치 가능 여부 검사
3. 타워별 설치 제한 검사
4. 자원 지출
5. 풀에서 오브젝트 획득과 그리드 등록
6. 마지막 건설 단계가 실패하면 같은 금액 환불

실패 사유는 `CannotPlace`, `LimitReached`, `NotEnoughCurrency`, `BuildFailed`처럼 구분해 반환합니다.

### 결과

경제 상태와 월드 상태가 함께 성공하거나 함께 복구됩니다. UI도 실패 원인을 구분해 정확한 피드백을 표시할 수 있습니다.

## 2. 다양한 크기와 특수 형태를 지원하는 그리드 점유

### 문제

일반 타워는 직사각형 크기를 갖지만 성벽은 두 첨탑, 여러 벽 셀과 중앙 성문으로 구성됩니다. 단일 셀이나 단순 가로·세로 크기만 저장해서는 두 형태를 함께 처리하기 어렵습니다.

### 해결

`GridBuildSystem`이 두 가지 footprint를 지원하도록 구성했습니다.

- 직사각형은 origin과 size로 셀 열거
- 특수 형태는 origin과 offset 목록으로 셀 열거
- 하나의 건물 인스턴스를 모든 점유 셀에 매핑
- 셀 하나를 선택해도 해당 인스턴스의 전체 점유 셀 제거

성벽은 `WallSpireLayoutCalculator`가 두 첨탑의 정렬과 최소 간격을 검사하고, 중앙 성문과 나머지 벽 셀을 계산합니다. 실제 생성 전에 전체 구조가 배치 가능한지 확인합니다.

### 결과

일반 건물과 조합형 구조물이 동일한 점유·검사·철거 API를 사용합니다. 새로운 비정형 건물도 offset 목록만 제공하면 확장할 수 있습니다.

## 3. 병영 여러 개가 공유하는 인구 자원의 경쟁 상태

### 문제

인구는 화면에 표시되는 총량과 이미 병사 모집에 사용 중인 양이 다릅니다. 여러 병영이 동시에 병사를 모집하면 각각 같은 잔여 인구를 보고 초과 모집할 수 있습니다.

### 해결

`PopulationReservationService`에 실제 총인구와 별도의 예약량을 두었습니다.

- 모집 직전에 필요한 인구를 원자적으로 예약
- 예약 성공 시에만 모집 슬롯 생성
- 병사가 사망하면 기존 슬롯을 유지한 채 지연 후 재생성
- 병영이 비활성화되거나 철거되면 모든 예약 반환

### 결과

여러 병영이 같은 인구 풀을 사용해도 가용 인구를 초과하지 않습니다. 사망과 재생성은 새로운 인구를 중복 소비하지 않으며 건물 생명주기와 예약 상태가 함께 정리됩니다.

## 4. 업그레이드와 상태 효과가 기본 스탯을 덮어쓰는 문제

### 문제

타워 업그레이드, 지속 피해, 회복과 다양한 버프가 같은 값을 직접 수정하면 적용 순서와 해제 시점에 따라 기본값을 잃거나 다른 효과까지 제거할 수 있습니다.

### 해결

런타임 스탯을 `StatModifierStack`으로 구성하고 modifier마다 source ID를 부여했습니다.

- ScriptableObject는 변경되지 않는 기본 스탯 보관
- 업그레이드는 고정 source ID의 배율 갱신
- 상태 효과는 자신만의 ID로 시작·Tick·종료
- 같은 ID의 효과를 다시 적용하면 이전 효과를 정상 종료한 뒤 교체
- 일시 효과와 영구 효과 목록을 분리

### 결과

서로 다른 시스템이 같은 스탯에 영향을 줘도 자신의 modifier만 갱신하거나 제거합니다. 프리팹 재사용과 풀 반환 시에도 런타임 상태를 명확하게 정리할 수 있습니다.

## 5. 웨이브 시스템과 주변 시스템의 결합도 낮추기

### 문제

적 생성이 끝나는 시점에는 주야 조명, 생산 보상, 병영 모집과 UI 등 여러 시스템이 반응해야 합니다. `WaveManager`가 이들을 직접 호출하면 기능이 늘어날수록 의존성이 커집니다.

### 해결

웨이브의 시작과 완료를 이벤트로 발행했습니다.

- `WaveStarted`: 밤 전환과 병영 모집 활성화
- `WaveCleared`: 낮 전환과 생산 건물 보상
- 적의 `Health.OnDied`를 구독해 생존 개체 수로 완료 판정
- 편대 데이터는 행·수량·깊이·간격과 지연 시간으로 구성

### 결과

웨이브 관리자는 적 편대와 생존 상태에만 집중합니다. 주야 연출과 경제 시스템은 독립적으로 이벤트를 구독하며 새로운 반응도 웨이브 코드를 수정하지 않고 추가할 수 있습니다.

## 6. 반복 생성되는 전투 오브젝트의 성능 비용

### 문제

웨이브마다 많은 적과 투사체가 생성·파괴되고, 병영의 병사와 건설물도 반복해서 재사용됩니다. 모바일 환경에서는 잦은 할당과 가비지 컬렉션이 프레임 저하로 이어질 수 있습니다.

### 해결

프리팹별 큐를 갖는 공통 `PoolManager`를 구현했습니다.

- 비어 있는 경우에만 새 인스턴스 생성
- 반환 시 비활성화하고 프리팹 전용 부모 아래 보관
- `PooledObject`가 원본 프리팹과 풀 상태 보유
- 중복 반환 방지
- 사전 생성과 활성·비활성 수 디버깅 정보 제공

### 결과

적, 병사, 타워와 투사체가 같은 풀링 규약을 사용합니다. 시스템마다 별도의 풀을 만들지 않고 생성과 반환 생명주기를 통일했습니다.
